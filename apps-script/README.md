# 백엔드 (Google Apps Script)

`Code.gs` 는 이 사이트의 백엔드 원본입니다. 실제로 도는 코드는 Google Apps
Script 편집기 안에 있고, 이 파일은 **그 사본**입니다. 편집기가 유일한 원본이
되는 상황을 막고 변경 이력을 남기려고 저장소에 둡니다.

**이 파일을 고쳐도 저절로 반영되지 않습니다.** 아래 배포 절차를 거쳐야 합니다.

## 어느 프로젝트인가

Google Drive의 **"사회자 대본 응답" 스프레드시트** → 확장 프로그램 → Apps Script.

Everafter에는 Apps Script 프로젝트가 두 개 있어서 헷갈리기 쉽습니다. 편집기를
열었을 때 아래로 구분하세요.

| | 이 프로젝트 (맞음) | 문의 응답 (아님) |
|---|---|---|
| 코드에 있는 것 | `function journeys_()`, `sheet_('여정', ...)` | `const SHEET_NAME = '문의'` |
| 하는 일 | 질문지·대본·여정·편지 | 홈페이지 문의 폼 접수 |
| 원본 위치 | 이 파일 | `Everafter-youngae/studio` 의 `apps-script/inquiry-handler.gs` |

## 고치고 배포하기

1. 이 저장소에서 `Code.gs` 를 수정하고 커밋
2. 전체 내용을 복사해 Apps Script 편집기의 기존 코드를 **전부 지우고** 붙여넣기
   (일부만 덮어쓰면 옛 함수가 남아 섞입니다)
3. 저장 (⌘S)
4. **배포 → 배포 관리 → 연필 아이콘 → 버전: 새 버전 → 배포**

4번까지 해야 실제로 바뀝니다. **저장만 하면 이전 버전이 계속 돕니다** — 가장
흔한 착각이니 주의하세요.

배포 후 URL이 바뀌지 않는 한 `shared.js` 의 `GS_URL` 은 그대로 두면 됩니다.

## 설정해야 하는 값

코드에 비밀값을 넣지 않습니다. 관리자 토큰은 편집기의
**프로젝트 설정 → 스크립트 속성**에 `ADMIN_TOKEN` 이름으로 저장하고, 코드는
`PropertiesService` 로 읽습니다. 이 값을 아는 사람만 관리 도구(`index.html`)를
쓸 수 있습니다.

### `BRAND_FROM` — 고객에게 보이는 보내는 사람 주소

메일은 **이 스크립트를 소유한 계정**에서 나갑니다. 그대로 두면 개인 지메일
주소가 고객에게 그대로 보입니다. 브랜드 주소로 나가게 하려면 두 가지가 모두
필요합니다.

1. 소유 계정의 Gmail → **설정 → 모든 설정 보기 → 계정 및 가져오기 →
   "다른 주소에서 메일 보내기" → 주소 추가** → 브랜드 주소 입력 →
   그 주소로 온 확인 메일의 링크를 눌러 인증
2. 스크립트 속성에 **`BRAND_FROM`** 이름으로 그 주소를 저장

별칭 인증이 끝나지 않은 주소를 넣으면 구글이 발송을 막습니다. 그래서 코드는
`BRAND_FROM` 으로 한 번 보내보고, 막히면 원래 주소로 다시 보냅니다 — 메일이
아예 안 가는 일은 없지만, 주소가 안 바뀌면 1번이 덜 끝난 것입니다.

## 브랜드 계정으로 옮기기 (소유권 이전)

메일은 **스크립트를 소유한 계정**에서 나가고, 시트도 그 계정 드라이브에
있습니다. 개인 계정으로 시작했다면 아래 순서로 브랜드 계정에 넘깁니다.
사본을 만들지 말고 **소유권을 이전**하세요 — 사본은 시트 ID가 달라져서
그때까지 쌓인 예식·여정·답장과 이미 나간 고객 링크가 끊깁니다.

1. **(이전 계정)** 스프레드시트 "사회자 대본 응답" → 공유 → 브랜드 계정을
   **편집자**로 추가 → 다시 그 사람 옆 메뉴에서 **소유자로 지정** → 이전
2. **(브랜드 계정)** 메일로 온 소유권 이전 요청 **수락**
3. **(브랜드 계정)** 시트 → 확장 프로그램 → Apps Script 로 열기
   - 스크립트 속성(`ADMIN_TOKEN`, `BRAND_FROM`)은 프로젝트에 붙어 있어
     그대로 따라옵니다. 프로젝트 설정에서 값이 있는지만 확인하세요.
4. **(브랜드 계정)** `authorizeMail` 실행 → 권한 허용
   (웹 앱은 **배포한 계정**으로 실행되므로, 브랜드 계정이 직접 배포해야
   메일이 브랜드 계정에서 나갑니다.)
5. **(브랜드 계정)** 배포 → **새 배포** → 유형: 웹 앱 →
   실행: **나** / 액세스 권한: **모든 사용자** → 배포 → **새 /exec 주소 복사**
6. 새 주소를 저장소의 **`shared.js` `GS_URL`** 과 관리 도구의
   **② 사전 질문 → 연결 설정 → 구글 앱스 스크립트 웹앱 주소** 양쪽에 반영
7. **(브랜드 계정)** 주간 백업 트리거 다시 만들기 — 트리거는 만든 계정에
   묶여 있어 따라오지 않습니다. 편집기 왼쪽 **트리거** → 백업 함수를
   매주 월요일 오전으로 추가
8. 이전 계정의 옛 배포는 **바로 지우지 말고** 1~2주 두세요. 링크에 배포
   주소가 박힌 긴 링크(`#id.key~배포ID`)를 받은 고객이 아직 있을 수 있습니다.

이전 뒤 확인: 관리 도구에서 **시트에서 불러오기**로 예식이 보이는지, 고객
화면 링크가 열리는지, 편지 발송이 되는지(보내는 사람 주소 확인) 세 가지.

## 시트

첫 요청이 오면 없는 시트는 자동으로 만들어집니다. 직접 만들 필요 없습니다.

| 시트 | 내용 |
|---|---|
| `설정` | 예식별 질문지 설정 |
| `응답` | 질문지·대본 검토 응답 |
| `대본` | 고객에게 발송한 대본 |
| `백업` | 대본 빌더 작업 데이터 |
| `여정` | 고객용 "두 분의 이야기" 공개 데이터 |
| `답장` | 예식 후 Everafter 편지 답장 |
| `문장DB` | 식전·식후 SNS 문장 마스터 목록 (직접 관리) |
| `링크키` | 예식별 링크키 (자동 발급 — 직접 건드리지 마세요) |

## 링크키 — 배포할 때 주의할 점

고객용 화면(`ask` / `review` / `story`)은 예식 ID나 영애 코드만으로는 열리지
않습니다. 예식마다 발급되는 14자리 링크키가 있어야 하고, 없으면 백엔드가
`{ok:false, error:'link key required'}` 로 거절합니다. 영애 코드는 `YYMM_NN`
연번이라 추측할 수 있기 때문에, 실제 인가는 링크키가 담당합니다.

링크키는 관리 도구가 링크를 만들 때 자동으로 발급받아 붙입니다. 사회자가
따로 할 일은 없습니다.

**링크키 검사 로직을 바꾸는 배포는 이미 보낸 링크를 전부 무효화할 수 있습니다.**
그런 배포를 했다면 진행 중인 예식마다 관리 도구에서 링크를 다시 복사해 재발송해야
합니다. 고객이 링크를 잃어버렸을 때의 복구 경로는 `story.html` 의 영애 코드 + 이름
조회(`?lookup=`)뿐이며, 이 경로는 링크키를 다시 발급해 줍니다.

## 계정 이전 — 트리거는 따라오지 않는다

이 프로젝트는 2026-09-11에 소유 계정을 `everafter.youngae@gmail.com` 으로
옮겼습니다. 그때 겪은 것들입니다.

**시간 기반 트리거는 파일이 아니라 사람에게 붙습니다.** 시트 소유권을 넘겨도
예전 계정의 트리거가 그대로 돌고, 새 계정에는 트리거가 없습니다. 새 계정에서
`installWeeklyBackupTrigger` 를 실행해 만들고, 예전 계정에서 따로 지워야
합니다. 순서를 거꾸로 하면 백업이 비는 구간이 생깁니다.

**그리고 트리거는 만든 사람이 승인한 권한 범위 안에서만 돕니다.** 코드에
나중에 추가된 스코프(여기서는 `DriveApp`)를 그 사람이 승인한 적이 없으면,
트리거는 매주 돌면서 매번 권한 오류로 죽습니다 — 아무에게도 알리지 않고.
실제로 `weeklyBackup` 은 이전 시점까지 **한 번도 성공한 적이 없었고**,
트리거 화면의 오류율 100%를 보고서야 발견했습니다. 백업 사본이 Drive에 정말
있는지 이따금 확인하세요. 트리거가 등록돼 있다는 것은 돌고 있다는 뜻이 아닙니다.

**새 계정에서는 함수를 한 번 수동 실행해 권한을 승인해야 합니다.** Apps Script
에는 "재승인" 메뉴가 없고, 실행할 때 뜨는 승인 창이 유일한 경로입니다.

**배포는 반드시 기존 배포를 편집(연필)해서 새 버전으로 올리세요.** `새 배포` 를
누르면 배포 ID가 바뀌는데, 그 ID는 고객에게 이미 보낸 링크의 해시
(`#<예식ID>.<토큰>~<배포ID>`)에 박혀 있습니다. 바뀌면 나간 링크가 전부 죽습니다.
새 계정이 다시 배포하기 전까지 웹 앱은 예전 계정 권한으로 계속 돕니다.

## 빌더 이전 예식의 후기 받기 (`thanks.html`)

빌더가 생기기 전에 함께한 분들은 예식 기록도 링크키도 없어 기존 답장 통로를
쓸 수 없습니다. 후기만 따로 받는 공개 링크를 위해 `pastReview` 통로가 있습니다.

**한 번만 해두면 되는 설정**

1. Apps Script → **프로젝트 설정 ⚙️ → 스크립트 속성**에 `REVIEW_KEY` 를 추가하고
   아무나 맞히기 어려운 문자열을 넣습니다.

   > **여기에 예시 값을 적어두지 마세요.** 이 레포는 공개입니다. 문서에 적힌
   > 문자열을 그대로 쓰면 누구나 이 통로로 글을 넣을 수 있습니다. 키보드에서
   > 아무렇게나 친 20자 정도면 충분하고, 어디에도 적지 않는 편이 좋습니다.
2. `Code.gs` 를 최신 내용으로 붙여넣고 **배포 → 배포 관리 → 연필 → 새 버전 → 배포**.
   (`새 배포` 를 누르면 배포 ID 가 바뀌어 고객에게 나간 링크가 전부 죽습니다)

**링크 만들기**

```
https://everafter-youngae.github.io/wedding-mc/thanks.html#<배포ID>.<REVIEW_KEY>
```

아래 형태도 모두 받습니다. `#` 뒤에 `&k=` 를 붙이면 해시 영역이라 값으로
읽히지 않는 게 원래 웹의 규칙인데, 링크를 손으로 만들다 보면 흔히 섞이므로
페이지가 네 가지를 다 받아줍니다.

```
#<배포ID>.<열쇠>      #<배포ID>&k=<열쇠>
#<배포ID>?k=<열쇠>    ?gs=<배포ID>&k=<열쇠>
```

**열쇠는 두 군데에 같은 값이 들어갑니다** — 스크립트 속성 `REVIEW_KEY`(서버가
대조할 정답)와 링크 끝(페이지가 내미는 답). 한쪽만 바꾸면 계속 거절당합니다.
속성 값은 바꿔도 재배포가 필요 없고, 저장만 하면 바로 적용됩니다.

배포 ID 는 웹 앱 주소의 `/macros/s/` 와 `/exec` 사이의 긴 문자열입니다.
이 한 줄을 예전 고객들께 그대로 보내면 됩니다. 예식마다 다르게 만들 필요가 없습니다.

**들어온 후기 보기**

빌더 상단 **편지 답장**에 다른 답장과 함께 뜹니다. 예식 월을 적어주신 경우
`예식 26년 8월 ·` 처럼 함께 표시됩니다. 공개 동의를 하지 않은 글은 그 화면에
나오지 않고 `답장` 시트에만 남습니다.

**막아둔 것**

- 링크에 실린 열쇠(`REVIEW_KEY`)가 맞지 않으면 거절합니다
- 사람이면 비워두는 칸(허니팟)이 채워져 있으면 조용히 무시합니다
- 문장이 둘 다 비어 있으면 저장하지 않습니다
